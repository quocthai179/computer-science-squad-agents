# Writing playbook

## Claims first, prose second

1. `claims.md` exists before any prose (Peyton Jones, Nanda). One piece, one main idea; 1–3 concrete claims.
2. Each claim points to evidence: `[run:<exp>-r003]`, `tables/<file>`, `figures/<file>`, `[@paper-id, §n]`.
3. Status: `supported` / `partial` / `unsupported`. An `unsupported` claim is never written as an assertion.
4. Limitations are mandatory.
5. G4: the user approves `claims.md` before `writer` writes.

## Writing (writer)

- Compress to bullets first, then write prose.
- The reader comes first: who reads it and what they already know (field `audience`).
- Contributions lead the piece; related work comes later.
- Numbers: copy them from `tables/` generated by scripts, with a table reference; never recompute, never round differently from the table.
- Citations as `[@paper-id, location]`; the id must exist in `papers/index.jsonl` or `papers/refs.bib`.
- Never write "novel", "first", "SOTA" (or "novateur", "首次", "初めて", "đầu tiên"...) when the idea card has no `closest_prior_work`.
- No placeholders in the final version.
- A survey is a *distilled* product (Olah & Carter, Research Debt): taxonomy, comparison, contradictions, gaps — not a list of per-paper summaries.
- Write in the project language (see `language.md`); keep anchors and numbers exactly as generated.

## Course reports

If the user has a style skill for reports in the project language (for example topic-research-report for Vietnamese), follow it: conclusion first (BLUF), pyramid structure, prose for explanations, tables for comparisons. Keep English technical terms where that is normal practice. Use Mermaid for diagrams if a mermaid skill is available.

## Check before review

```bash
python3 <plugin>/scripts/cite_check.py <file>
python3 <plugin>/scripts/lint_report.py <file>
```

Both must be clean before the final `skeptic` round.

## Reproducibility checklist (Pineau, condensed)

- [ ] model, algorithm and assumptions clearly described
- [ ] data: source, split, preprocessing, number of samples
- [ ] hyperparameters: range tried, how chosen, final values
- [ ] number of seeds, how variance is reported (mean ± CI)
- [ ] compute: hardware, time
- [ ] code and config traceable to the git SHA in the ledger
- [ ] metric defined clearly; eval protocol unchanged across variants

## Explain-back (G5)

Before submission the Lead asks the user 3 questions about the document itself (why claim C1 holds, what would refute it, the biggest limitation). Any part the user cannot explain is not ready.

State the level of AI assistance as the course or venue requires.
